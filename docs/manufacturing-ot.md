# Optional manufacturing OT cell (SIMU-54)

Manufacturing can execute pump batches through real OpenPLC, a discrete equipment
model and an editable FUXA HMI. `OT_MODE=disabled` is the default. The Java backend
owns business transactions, materials, line/output capacity, audits and completion
events. Equipment has no manufacturing database credentials; native HELICS stays
in the existing private adapter. Twin remains an optional observer.

## Deployment

Use `apps/manufacturing/compose.v1.yaml` with `apps/manufacturing/compose.ot.yaml`
for a **new independent deployment**. Copy `apps/manufacturing/ot.env.example`
to an ignored private env file, replace credentials, and create the employee and
FUXA identities in `MANUFACTURING_IDENTITIES`. Give FUXA `status:read` and
`runs:control`; add `scenarios:manage` only when its fault-injection tools are needed. the proxy supplies that identity server-side. Do not put credentials
in the checked-in FUXA project. Existing standalone packaging is unchanged.

Run from the repository root, using the same private env file/project for every
command. For example, with `OT_ENV` set to its path:

```sh
python3 scripts/docker_guard.py --wait --label manufacturing-ot-build -- docker compose --env-file "$OT_ENV" -p manufacturing-ot -f apps/manufacturing/compose.v1.yaml -f apps/manufacturing/compose.ot.yaml --profile local build
python3 scripts/docker_guard.py --wait --label manufacturing-ot-start -- docker compose --env-file "$OT_ENV" -p manufacturing-ot -f apps/manufacturing/compose.v1.yaml -f apps/manufacturing/compose.ot.yaml --profile local up -d manufacturing-api manufacturing-worker manufacturing-controller manufacturing-web fuxa
python3 scripts/docker_guard.py --wait --label manufacturing-ot-hmi -- docker compose --env-file "$OT_ENV" -p manufacturing-ot -f apps/manufacturing/compose.v1.yaml -f apps/manufacturing/compose.ot.yaml run --rm --no-deps ot-fuxa-bootstrap
```

The local profile supplies owned PostgreSQL/RabbitMQ. Hosted role placement must
supply its own URLs/private routing and secrets. No hosted deployment or automatic
live cutover is performed by this change. API readiness requires worker/controller
heartbeats; physical readiness is separately visible at `/api/ot` and in FUXA.
Web defaults to localhost:8083; FUXA defaults to localhost:1881. Keep OpenPLC,
Modbus, equipment and the HMI proxy private. Configure FUXA authentication and
TLS at the deployment boundary before exposing its editor beyond localhost.

The compiler and OpenPLC images, compiler archive checksum and FUXA image are
pinned in the OT Dockerfiles/overlay. OpenPLC v4.3.1 executes the STruC++ 0.7.0
output for `apps/manufacturing/ot/plc/cell.st`. The IEC file can be opened in the
matching OpenPLC Editor v4.3.2; rebuild/provision an isolated cold runtime after
editing it. Hot program replacement is deliberately refused. Runtime build and
source hashes are persisted and verified before restarting a known program.

FUXA starts from `ot/fuxa/project.json`, generated by `build_project.py` from
`cell.svg` and `client.js`. Import/export and edit it in the native FUXA editor.
Normal bootstrap preserves an existing project. `--replace-owned-project` is an
explicit development operation restricted to the seeded SIMU-54 view; do not use
it to overwrite operator edits. Its HTTP connector uses native FUXA tags, including
one coherent frame and one command mailbox; raw PLC registers are not writable
from the HMI.

## Operating a batch

1. In Manufacturing, supply BOM material, create and release a PUMP work order.
   Java consumes/reserves inputs once and dispatches one batch carrier to the cell.
   The cell adds a one-batch capacity limit even if business line capacity is two.
2. In FUXA, check the run/epoch, active order and Connected status, then Start.
   The carrier moves through positioning, clamping, processing and exit using
   actual PLC actuator feedback. The schematic represents one whole batch.
3. Stop pauses without returning consumed material. Fault controls inject/restore
   conveyor jam, position sensor failure, open guard and power loss. Each fault
   inhibits actuators and latches. Restore the condition, Reset/acknowledge, then
   Start; Reset does not erase batch progress or clear an unsafe condition.
4. Java requires a correlated equipment completion before committing good output,
   scrap, custody/provenance and its existing completion event. An elapsed business
   timer alone cannot complete OT production. Output capacity still applies; the
   equipment fact remains durable while Java waits for capacity.

Commands show pending/completed/rejected status. An uncertain command is retained
in browser session storage and Retry resends its exact identity/body. Discard
removes only the local retry; it does not cancel a command already accepted.
Employee identities cannot operate the cell. Operator commands are audited and
fenced by run and epoch. State-dependent admission rejections are durable receipts;
retrying a rejected Start after Resume keeps the rejected outcome. `/api/ot/tags` exposes the scoped HMI interface;
`/api/ot/commands` is the authenticated operator API.

## Time, durability and recovery

An enabled run requires integer `HANDOFF_QUANTUM`. Java admits consecutive
one-second equipment steps only through `floor(actual persisted granted time)`.
Requested native time is never permission to move. Earlier native grants bound
catch-up; controls/dispatch accepted at the current grant cannot change past
intervals. Each actual running grant atomically records its authorised intervals before Hold can interleave. Hold settles those already admitted intervals but admits no new steps. A held run can still acknowledge Stop and fault controls after those intervals settle. Large handoff quanta can therefore delay Stop at that boundary; the default quantum is one second. Speeds
1/5/20/60 are nominal ceilings: every step still needs a scan acknowledgement.
The PLC scans at 100ms on Docker's normal scheduler; deterministic wall-clock
scan timing and guaranteed 60x throughput are not claimed.

The equipment journal persists intent before PLC I/O and receipt/model state
after the echoed sequence and scope cookie. Exact duplicate commands replay the
same receipt. Transactions do not span network calls. Each request uses a 16-bit
Modbus transport transaction ID (which can wrap); the independent logical PLC
sequence **must not wrap**. Before 65,535 acknowledged operations, perform a
controlled new epoch (less than 18.2 simulated hours including commands).

A transient network loss retains the same pending operation for retry and shows
stale/disconnected status. Unknown physical state is never converted into a
business completion. An equipment process restart, a PLC cookie/sequence mismatch,
or a new controller owner on the same epoch requires reconciliation and a new
run/epoch. Archive the old run and reconcile already-consumed batches/output with
its business records; the simulator does not automatically reconstruct a live
batch. Use the operator's confirmed run reset in standalone mode, then restart a
controller that stalled. A finalised standalone controller remains available for
a confirmed new run. Connected HELICS runs must be finalised and allocated a new
federation run/epoch; live connected reset is forbidden.

Enabling OT on an existing disabled deployment takes effect after a confirmed
reset. Starting a persisted enabled run with disabled configuration is refused. To return to disabled execution, finalise/archive the OT deployment and provision an independent fresh disabled deployment; removing the overlay is not a live mode switch.
Finalization waits for current business/physical work to settle and a real stopped
PLC acknowledgement. Preserve the equipment, PLC runtime/build, FUXA and business
data volumes across routine container recreation. Do not prune live volumes.
Migration `016_manufacturing_ot.sql` adds the optional run mode and durable OT
records without changing applied migrations or public cross-department contracts.

## Modbus register map

Unit 1, FC3 reads and FC16 writes, unsigned 16-bit words, network big endian.
Explicit segmented mapping puts `%QW0` at holding address 0 and `%MW0` at 1024;
the runtime's legacy default does not expose `%MW`. Inputs are written/read back
before request-sequence commit; echoed scope and sequence fence the result.

| Input address | Meaning |
| --- | --- |
| 1024–1026 | enable, guard closed, power available |
| 1027 | request sequence, written last |
| 1028–1032 | positioned, clamped, processed, exited, healthy |
| 1033–1037 | batch number, target good/scrap, reset fault, active batch |
| 1038–1041 | four-word run/epoch/controller-session cookie |
| 1042 | initialise/reset cell scope |

| Output address | Meaning |
| --- | --- |
| 0 | acknowledged sequence |
| 1–4 | conveyor, clamp, cycle, fault |
| 5–7 | good, scrap, current batch number |
| 8–11 | echoed scope cookie |

Outputs are read between two sequence reads to reject torn snapshots. PLC scans
with unchanged request markers do not advance the model. See the private
[HTTP contracts](../contracts/ot/v1/README.md) and
[acceptance evidence](simu-54-acceptance.md).
